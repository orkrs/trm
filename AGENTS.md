# AGENTS.md: Системные правила написания кода и регламент разработки

Этот документ содержит свод обязательных правил, стандартов и инструкций для ИИ-кодера. Любой генерируемый код, структура файлов и процесс разработки должны беспрекословно соответствовать данным требованиям.

## 1. Технологический Стек Проекта (Technology Stack)

- **Язык программирования:** Python версии 3.10 или выше (использование современных возможностей, включая match-case, новые синтаксические конструкции аннотации типов).
- **Глубокое обучение:** PyTorch версии 2.4 или выше (обязательное использование преимуществ PyTorch 2.x, таких как torch.compile при необходимости).
- **Вычисления на GPU:** CUDA версии 12.1 или выше.
- **Модели пространства состояний:** Официальная библиотека mamba-ssm, einops (для декларативных тензорных трансформаций).
- **Символьные вычисления:** SymPy версии 1.12 или выше.
- **Оптимизация и ограничения:** Google OR-Tools версии 9.8 или выше.
- **Векторный поиск:** FAISS (библиотека faiss-cpu или faiss-gpu) версии 1.8 или выше.
- **Вспомогательные инструменты:** NumPy, pydantic (для строгой валидации конфигураций), loguru (для структурированного логирования).

## 2. Стандарты Написания Кода (Code Style & Quality)

### 2.1 Аннотация типов и Сигнатуры (PEP 484)

- Все функции, методы класса, генераторы и корутины должны содержать полные аннотации типов для всех аргументов и возвращаемых значений.
- Использование типа `Any` категорически запрещено. В случае неопределенности типа следует использовать `Union`, `TypeVar` или встроенные генерики (`Generic`).
- Для сложных структур данных или конфигураций необходимо использовать структуры `dataclasses` или модели `pydantic.BaseModel` с обязательной валидацией типов при инициализации.
- Если функция возвращает несколько значений, они должны быть явно типизированы через кортеж `Tuple[Type1, Type2, ...]`.

### 2.2 Документирование и Комментарии (PEP 257)

- Каждый класс, модуль, функция и метод обязаны иметь подробную документацию (docstring) строго в стиле Google.
- Документация должна содержать три обязательных раздела: детальное описание поведения (Args), спецификацию типов аргументов и описание возвращаемого значения (Returns), а также возможные возбуждаемые исключения (Raises).
- В комментариях и документации запрещено использовать длинные тире (знаки "—" или "--"). Вместо них следует использовать двоеточия, запятые или перефразировать предложения.

### 2.3 Контроль размерностей тензоров (PyTorch Shape Tracking)

- Любая строка кода, выполняющая операции над тензорами (срез, транспонирование, умножение, свертка, сканирование), обязана сопровождаться комментарием с указанием размерности тензора на входе и на выходе.
- Формат комментария должен отражать буквенные обозначения осей: `B` (Batch), `L` (Length), `D` (Dimension), `R` (Rank), `C` (Channels).
- Пример правильного комментирования:
  ```python
  # x: (B, L, D) -> входной тензор
  x = torch.einsum('b l d, d r -> b l r', x, self.proj_matrix)
  # x: (B, L, R) -> тензор после MIMO проекции
  ```
- Для изменения порядка осей тензоров или их объединения необходимо использовать декларативный синтаксис `einops.rearrange` или `einops.repeat` вместо нечитаемых цепочек методов `.transpose().contiguous().view()`.

## 3. Специфические Правила Работы с PyTorch и Памятью

### 3.1 Управление устройствами (Device Management)

- Прямое жесткое указание устройства в коде через строковые константы вроде `.to("cuda")` или `.to("cpu")` запрещено.
- Все операции по переносу тензоров должны использовать централизованный объект устройства, определяемый в конфигурационном файле проекта: `device = config.device`.
- При создании новых тензоров внутри методов (например, масок или начальных состояний) необходимо явно передавать аргументы `device=device` и `dtype=dtype`, избегая лишнего копирования между хостом и видеокартой.

### 3.2 Контроль градиентов (Gradient Control)

- При работе с замороженным ядром модели необходимо принудительно отключать вычисление градиентов для всех слоев базовой сети.
- Запрещено полагаться на неявное поведение PyTorch. Процесс заморозки должен выполняться явно:
  ```python
  for param in backbone_model.parameters():
      param.requires_grad = False
  ```
- Все блоки кода, выполняющие инференс, оценку качества или валидацию, должны быть обернуты в контекстный менеджер `with torch.no_grad():`.

### 3.3 Предотвращение утечек памяти и In-place операции

- Запрещено использовать операции изменения тензоров на месте (in-place операции, такие как `+=`, `*=`, `.add_()`), если они могут нарушить граф автоматического дифференцирования PyTorch.
- При итеративной работе рекурсивного ядра необходимо своевременно вызывать метод `.detach()` для тензоров, которые передаются между шагами рекурсии, но не требуют сохранения истории градиентов для предотвращения накопления неиспользуемой памяти графа автограда.

### 3.4 Обеспечение воспроизводимости (Determinism)

- Весь генерируемый код инициализации весов и случайных проекций обязан использовать фиксированные генераторы случайных чисел (seeds).
- В начале выполнения проекта должен вызываться централизованный метод фиксации состояния:
  ```python
  torch.manual_seed(config.seed)
  torch.cuda.manual_seed_all(config.seed)
  np.random.seed(config.seed)
  ```

## 4. Архитектурный Дизайн Кода (Software Engineering Principles)

### 4.1 Единственная ответственность (Single Responsibility Principle)

- Каждый класс должен отвечать только за один логический компонент архитектуры. Запрещено смешивать логику хранения памяти, вычисления переходов модели и принятия решений о распределении бюджета в одном файле или классе.
- Все математические преобразования и внешние символьные среды (SymPy, OR-Tools) должны быть изолированы в виде отдельных провайдеров услуг с четко определенными интерфейсами (интерфейсные классы-обертки).

### 4.2 Обработка исключений и Логирование

- Категорически запрещено использовать пустые блоки перехвата исключений `except: pass` или перехватывать базовый класс `except Exception:`.
- Все исключения должны быть типизированы. Для специфических ошибок архитектуры (ошибки парсинга кода, ошибки переполнения памяти, сбои транслятора) необходимо объявить кастомные классы исключений, наследуемые от `Exception` или `ValueError`.
- Все критические точки выполнения кода (инициализация весов, выделение памяти, старт аукциона, внешнее выполнение кода) должны сопровождаться записью структурированных логов через библиотеку `loguru` с указанием уровня важности (INFO, WARNING, ERROR).

## 5. Регламент Взаимодействия с ИИ-кодером (Workflow)

Процесс написания кода должен быть строго разбит на фазы. ИИ-агент обязан соблюдать следующую дисциплину разработки:

1.  **Фаза планирования:** Перед написанием любого программного файла ИИ-кодер обязан предоставить текстовое описание архитектуры модуля, список входящих и исходящих типов данных и обоснование выбора конкретных математических функций PyTorch.
2.  **Фаза инкрементальной реализации:** Код пишется небольшими логическими блоками (не более 150 строк за один раз). Запрещено генерировать весь проект в одном сообщении.
3.  **Фаза верификации кода:** Для каждого написанного модуля ИИ-кодер обязан составить простой юнит-тест (с использованием библиотеки `pytest` или встроенного модуля `unittest`), проверяющий размерности выходных тензоров на синтетических данных.
4.  **Правило остановки:** После написания каждого файла или прохождения фазы верификации ИИ-кодер останавливает генерацию и запрашивает подтверждение пользователя: «Блок [Имя_Блока] успешно протестирован. Могу ли я перейти к следующему шагу?».
